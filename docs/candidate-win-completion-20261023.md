# 후보 착수 뒤의 강제승을 먼저 검증 — v5.18.3

자동·심층이 좋은 수를 임시 후보로 보여주면서도 승리 증명을 뒤로 미루는 경로를 수정했다. **내 후보의 승리가 실제로 증명되면** 나머지 비교를 중단하고 확정한다. 패배·방어·저항 분석에는 새 조기 종료 조건을 추가하지 않았다. 빠르게 1초, 자동 최대 15초, 심층 최대 25초와 기존 규칙·모델·신경망 입력은 유지한다. 학습은 재개하지 않았다.

## 남아 있던 원인

v5.18.1은 이미 증명된 승리 결과의 Worker 전달을 고쳤다. 이번에 확인한 경로는 **후보를 실제로 검증하는 시점**이다. 높은 제한 탐색 점수에는 아직 증명이 없었고, 착수 뒤 상대 차례를 검사하면 바로 찾을 수 있는 전체 응수 증명을 후보 비교 도중에 수행하지 않았다. 기존 심층의 마지막 확인은 `5e7` 이상의 점수를 요구했지만 Reader의 승리 기준은 `1e7`이어서, Reader가 약 999만 점을 준 후보는 이 조건에도 들어가지 않았다. 점수만으로 승리로 올리는 수정은 하지 않는다.

생성 국면의 내 돌은 `E8 F8`, 상대 돌은 `C8 D7 D9 C7 E9 H7 G7 I9 H9`이며 내 차례다. 좌표는 테스트의 **A1=배열 0** 표기다. `G8` 전에는 직접 VCF가 없고, `G8`을 둔 뒤 상대의 **208개 합법 응수 전부**에 이기는 후속 수순이 있다. 수정 전 엔진은 같은 후보에 약 999만 점을 주면서도 `proven:false`로 반환했다. 수정 후에는 전체 응수 증명과 `verified-win`으로 확정한다. 최근 사용자 대국 기보는 기억나지 않는다고 답변했으므로, 이를 그 실제 대국의 재현이라고 주장하지 않는다.

## 변경 내용

- `verifyWinningMove`는 내 후보를 복사한 보드에 둔 뒤 **실제 다음 차례인 상대**의 모든 합법 응수를 검사한다. 상대의 즉시 승리·반격 4·강제 방어도 포함한다. 일부 응수의 성공이나 미완료 검사를 증명으로 사용하지 않는다.
- 직렬 탐색은 유망 후보를 진행 메시지로 내보내기 전에 짧게 검증한다. 성공하면 증명을 전달하고 현재 탐색을 종료한다. 실패·시간 초과는 일반 비교를 계속한다. 한 분석의 후보 검사는 최대 4회이며 총 예약은 긴 모드 320ms, 짧은 모드 80ms 안에서 사용한다. 후보 한 번의 검사는 최대 160ms이고 전체 남은 시간도 확인한다.
- 병렬 탐색은 완료된 동일 깊이 비교 뒤 기존 Worker 하나에서 후보를 검증한다. 증명되면 직렬·병렬 Worker와 타이머를 종료한다. 미완료·다른 후보의 증명·이미 반증된 후보·늦은 결과는 확정하지 않는다. 새 Worker 수를 늘리지 않는다.
- 인증에는 원래 보드·후보 뒤 보드 키와 전체 응수 분기 트리를 남긴다. 세부 분기를 생략한 일반 탐색 캐시를 재사용하지 않고 작은 인증을 자체 생성한다. 실패한 검사도 노드·시간을 기록하도록 `counterLoss` 조기 반환의 노드 누락을 보완했다. 일반 탐색 캐시의 의미와 `node-v3` 이름은 유지하고, 엔진 표시는 `unified-initiative-2-forbidden-1-candidate-win-1`로 구분한다.

## 검증

`test/candidate-win.cjs`는 흑백·회전·반사 16개 사례의 **3,328개 실제 상대 응수**를 별도 규칙과 증명 DAG 검사로 검증한다. 실제 빠르게·자동·심층 분석이 같은 후보를 증명하고 진행 결과에서 조기 완료함을 확인한다. 반격 4, 상대 즉시 승리, 3·3 금수, 장목, 정확한 5목 우선, 시간 초과·엔진 재사용·보드 복원과 기존 강제패배 분석을 검사한다.

`test/candidate-win-ui.cjs`는 공개 기본 외형·모델 없는 생성 fixture에서 실제 Edge Worker를 사용한다. 자동 15초·심층 25초와 흑백을 정상 전달 및 직렬 메시지 보류 조건으로 나눈 8개 사례를 검사한다. 후자는 병렬 Worker가 실제로 임시 후보를 비교한 뒤 208응수 인증을 직접 만들었는지 확인한다. 모든 사례가 `분석 완료 · 강제승`, 완료 콜백 1회, 활성 Worker 0개였으며 인증을 별도 재검증했다. 이 단순 국면의 마지막 실행은 약 0.50~0.67초였고 보편적 속도 보장은 아니다. 최초 UI 검사에서는 앱 초기화가 검사 시작 직후 분석을 다시 요청해 테스트 작업을 취소했다. 초기화를 안정시킨 뒤 실제 경로를 검사했다.

기존 `proven-win-latency.cjs`의 단일 VCF 재생은 새 전체 응수 인증의 대표 수순과 형식이 달라 실패했다. VCF는 기존 검사, 전체 응수 인증은 착수 뒤 보드에서 모든 응수 루트를 독립 검증하도록 구분했다. 전체 응수 루트를 검사하기 전 후보 자체의 합법성과 대표 수순의 교대 착수·5목 종료도 별도 규칙으로 확인한다. 승리 주장이나 반격 조건을 완화하지 않았다. 기존 병렬 동일 깊이·최종 방어·취소·늦은 결과 검사도 유지한다. 기존 UI의 진행 전달 검사는 최종 메시지를 진행 메시지로 바꾼 경우만 기록했으나, 이제 그 전에 도착하는 실제 승리 진행 메시지도 기록한다. 화면의 강제승·완료·Worker 종료 단언은 그대로다.

공개 HTML의 기존 Edge 검사도 재실행했다. 일반 국면은 자동 24후보·깊이 5, 심층 32후보·깊이 6을 완료했고 합법 PV·Worker 정리를 확인했다. 기존 강제승 전달의 16개 경로와 금수 유도 최종 방어 검사도 통과했다. 금수 함정 후보는 흑백 각각 198개 응수 증명으로 배제하고 합법 공격 대안은 유지한다. 이 방어 국면의 일반 자동·심층 결과는 여전히 미확정이므로 안전·필승으로 확대하지 않는다. 기존 병렬 UI 검사는 입력 대상만 공개 `dist/index.html`로 지정했고 검사 논리를 바꾸지 않았다.

전체 `npm test`는 종료 코드 0이며 통합 35개 시나리오의 실패는 0개다. 최초 실행의 위 인증 형식 검사 실패는 보완 후 통과했고, 이후 후보 인증·기존 강제승 지연·UI 전달 검사 변경분도 각각 재통과했다. 예산·Worker·캐시·공격 지속·방어와 역공·기보·규칙 및 생성 fixture 기반 학습 연속성 검사도 포함한다. 실제 중단 실험의 학습·평가를 다시 실행한 결과가 아니다.

검사 상세와 수정 전 실행기·원본 해시·비교 결과는 ignored `work/candidate-win-20261023/`에 보존한다. 작은 국면의 승리 확정 개선이며 장기 대국 기력 향상이나 모든 강제승의 즉시 발견을 뜻하지 않는다. 후보가 아직 발견되지 않았거나 제한 시간 내 전체 증명이 되지 않으면 분석을 계속한다.

## 학습과 배포 경계

기존 실험 3개의 상태·진행·설정·후보·학습 보고·optimizer 체크포인트·미완료 평가, 활성 모델과 개인 외형 등 보호 파일 **21개 SHA**가 작업 전과 같은 것을 확인했다. 중단된 trial 95 / cycle 1은 **934/6,800, stopped** 상태다. 기존 실행이나 평가 식별자를 새 엔진으로 덮어쓰지 않는다. 현재 소스 식별자는 `6ad08b5cc1f6d326830ae296c38045d96121a05e371124b1fd1e5600d2a43f87`이다.

학습실에서 보존된 실행을 그대로 재개하면 원래 엔진을 사용하는 경계도 유지한다. 이번 엔진으로 경험·유효 가중치를 이어갈 때는 정상 `--from-run`을 통한 **새 run과 새 평가**가 필요하다. 이번 작업에서는 실행하지 않았다. 기존 채택 모델은 보존하며 미완료 평가를 채택으로 표시하지 않는다.

공개 배포는 `dist/index.html`, 개인 외형·기존 저장 키를 쓰는 로컬판은 ignored `outputs/omok.html`이다. 개인 외형과 학습 원본은 Git에 올리지 않는다.
